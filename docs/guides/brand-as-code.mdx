---
title: Brand as code
description: Keep a brand's rules, pages and theme as files in a Git repository, changed on either side.
---

A brand can live in a Git repository as well as here: its rules, pages and
theme as YAML a person reads and reviews, beside the files they point at.
Change it in the repository, through a pull request, or here, in the
builder: each side's changes reach the other, and a change that both sides
made to the same rule is named, not lost.

## The files

```
brand/
  brand.yaml          slug, name, theme, the order of rules/, the page tree
  rules/color.yaml    the rules whose key starts with color.
  rules/logo.yaml
  pages/overview.yaml a page: its fields and sections
  pages/logo.yaml
  assets/logo.svg     files the rules and pages point at
```

```yaml brand.yaml
# An Artbucket brand: rules in rules/, pages in pages/, files in assets/.
slug: acme
name: Acme
theme:
  accent: color.primary
  radius: 6
rules: [color, type, logo, tone]
pages:
  - overview
  - logo:
      - logo-use
  - color
```

```yaml rules/color.yaml
color.primary:
  type: color
  label: Acme blue
  value: "#1f6feb"
  usage: Buttons, links and the mark's tile.
  spec:
    pair: color.background
    cmyk: [89, 55, 0, 8]
  contexts:
    dark-background:
      value: "#58a6ff"
```

```yaml pages/logo.yaml
title: Logo
lede: One mark, and how to give it room.
sections:
  - template: logos
    title: Versions
    keys: [logo.primary, logo.mark]
  - template: dodont
    items:
      - asset: assets/logo-stretched.png
        verdict: dont
        caption: Never stretch it.
```

Each rule, page and section takes what the API takes
([the canon](/guides/canon)). A file leaves out every default: a section's
width, tone and columns come from its template unless set, and its id is its
template's name (`logos`, then `logos-2`) unless it has one of its own.
Where an asset id goes, a path under `assets/` goes too.

## Pushing and pulling

```bash
artbucket brand pull brand --brand acme --assets   # acme as files in brand/, with its assets
artbucket brand diff brand                         # what a push would change
artbucket brand push brand                         # take the brand from its files
```

`push` uploads what `assets/` adds, checks every file, and writes the brand
as one version of its history, so it is undone like any other edit. A
problem comes back at its file and line:

```
pages/color.yaml:6: sections[0].keys[0]: no rule "color.nope"; this brand has color.primary, color.ink
```

`pull` writes only the files whose meaning changed: a file that says the same
keeps its comments and its layout.

Each command acts on the brand `--brand` names, or else the one `slug:` in
`brand.yaml` names (`pull` writes it), never on the workspace's default. A
`brand.yaml` whose slug names another brand is refused, so files pushed to
the wrong brand never land. `push --create` makes the brand when there is
none by that slug.

## From CI

Without a Git integration (a self-hosted server, or a team that would rather
not install one), a CI job does the push. Make a write key once, keep it as
a secret with the server's address, and push the brand's folder when it
changes on the main branch:

```bash
artbucket keys create ci --scope write
```

```yaml .github/workflows/brand.yml
name: Brand
on:
  push:
    branches: [main]
    paths: ["brand/**"]
jobs:
  push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - run: npx --yes artbucket brand push brand --brand acme --publish --note "$(git log -1 --format=%s)"
        env:
          ARTBUCKET_URL: https://app.artbucket.io
          ARTBUCKET_KEY: ${{ secrets.ARTBUCKET_KEY }}
```

```yaml .gitlab-ci.yml
brand:
  image: node:22
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      changes: ["brand/**/*"]
  script:
    - npx --yes artbucket brand push brand --brand acme --publish --note "$CI_COMMIT_TITLE"
```

On GitLab, `ARTBUCKET_URL` and `ARTBUCKET_KEY` are CI/CD variables, the key
masked. `ARTBUCKET_URL` is your own server when you host one. Without
`--publish` the push updates the draft, to release from the app. On a pull
or merge request, `artbucket brand diff brand --brand acme` exits 1 on any
problem in the files, at its line, which makes it a check.

## A README badge

A public, released brand has a badge on BrandHub with the release that is
live, "brand @4", at `/{org}/{brand}/badge.svg`. The brand's Settings,
under BrandHub, give its Markdown:

```md
[![Brand on BrandHub](https://hub.artbucket.io/acme/acme/badge.svg)](https://hub.artbucket.io/acme/acme)
```

It follows each release, answers for public brands only, and showing it is
not counted as a read of the brand.

## Both ways

A brand kept in a repository remembers where (`PUT /api/v1/brands/{slug}/source`)
and what the two last agreed on. From then on:

- **The repository changes** (a push to its branch): `POST .../files/import`
  with the files and their `commit`. What was edited here since the last sync
  is kept; the files win only where both sides changed the same rule, page or
  theme setting, and the answer names each in `conflicts`. The side that lost
  is in the brand's history, a restore away.
- **The brand changes here**: the source reads `pending`. `POST .../files/export`
  with the repository's files as `previous` answers the files to commit, only
  those that changed. Commit them, as a commit or a pull request, then send
  them back with `PUT .../source` and `synced: { commit, files }`.

An import at a commit names the version it makes after the commit's message,
so each sync stands in the history on its own.

## Previews

`POST /api/v1/brands/{slug}/previews` with a pull request's files and a `ref`
(`pull/12`) answers a link to the brand's site as those files say it, and
what it would change. It needs no account, like a share link, and keeps its
address as the pull request changes. Delete it when the pull request closes.

## From the app

Where the server has a Git integration (`GIT_CONNECT_URL`), a workspace admin
reaches it from three places:

- **New brand, From a Git repository:** bring in a brand a repository already
  holds (its `brand.yaml`, pages and files), or start a new brand here and
  keep it in a repository from the first edit.
- **A new brand's setup:** connect a repository before laying out any page.
- **The builder's bar:** Git, until the brand is kept somewhere; then the
  repository, and whether both sides are in step.

The integration sends you back to the brand's Overview, which says when the
first sync has landed and offers Release while readers don't see it yet. On
the welcome page, the path for a product's brand and design system starts
there too: "My brand is already in a repository" brings it in.

## On Artbucket Cloud

Artbucket Cloud connects a GitHub repository to a brand from any of those
places, and does all of the above itself: pull requests get a check, a
preview link and a comment listing what they change and what merging does,
merges come in, and edits made here go back as a commit or a pull request.

The connection also decides what a change that reaches the branch does:

- **From Artbucket:** a merge updates the draft, and someone releases it here.
- **When a change is merged:** each push to the branch, a merged pull request
  too, is released, with its commit's first line as the note.
- **On a GitHub release:** a merge updates the draft, and publishing a
  release on GitHub releases its tag, with the release's title as the note.

Neither releases while edits made here wait to reach the repository: the
check says so, and the next merge or release carries both. Each release
from the repository posts a GitHub deployment (environment `Artbucket`)
linking to the brand on BrandHub or its portal, so the repository's
sidebar shows what is live. Without the App, [a CI job](#from-ci) does the
push.
