Brand rules are records, not a PDF: a dotted key, a typed value (`color`,
`text`, `number`, `list` or `font`), a sentence on how to use it, and the assets
it points at.

```bash
pnpm artbucket rules set color.primary '#34a853' --type color --usage "Buttons, links, the mark's tile"
pnpm artbucket rules set color.primary '#5bc27a' --type color --context dark-background
curl 'https://assets.example.com/api/v1/brand/rules?context=dark-background'
```

A rule can be scoped to a context. Asking for one returns one rule per key:
the context's own where it has one, the default otherwise.

## The guidelines page

Guidelines, in the sidebar, is drawn from those records and edited in place:
click a value to change it, press `/` to add a rule from named building blocks
(brand color, clear space, logo don'ts, type scale, words to avoid), drag to
reorder. Colors show their contrast on white and black, a numeric `type.scale`
renders as a specimen. An attached asset can name a rendition (`w_512,f_png`):
agents then get that exact URL.

## Brand pages

A brand with no pages opens on its setup: the main color (and a second and a
dark one), a heading face and a text face from Google Fonts, the logo and a
sentence of voice, with the cover beside them as it will look. They become the
rules `color.primary`, `color.secondary`, `color.dark`, `type.heading`,
`type.body`, `logo.primary` and `tone.voice`, and the pages are laid out from
them; a blank page or a topic's six pages are the other starts. In the builder,
the page list sits beside the canvas, and the bar names what an editor reaches
for: Add, Rules and Theme, then the launch checklist, Preview and Publish. The
checklist is the brand's steps to being worth sharing (colors, typefaces, logo,
voice, pages, a publish, a portal), each with where it is done; agents read the
same list with `brand_status`, or `GET /api/v1/brands/{slug}/status`.

The rules are the content; pages lay them out for people. A brand's pages
form a tree, up to three levels deep (Overview, then Identity with Color, Logo
and Type under it), and each page is sections built from templates: a cover,
a palette, type specimens, logo rules, do's and don'ts, a gallery, a live
collection. A section shows rules by key and never copies a value, so change
`color.primary` and every page that shows it follows.

```bash
pnpm artbucket templates                  # what each template shows and binds
pnpm artbucket pages generate             # a first layout from the rules
pnpm artbucket page save color color.json # make or replace a page whole
pnpm artbucket page color                 # a page as Markdown
```

A page reads as a chapter of the book (`layout: book`, the default: the nav
beside it, on-this-page, and the next page at its foot) or as a front
(`layout: landing`: none of those, for a home or a campaign page). Its
`audience` says who may read it on a portal, and `hidden` keeps it from
readers altogether. The theme (`/api/v1/brands/{slug}/theme`) says which rules
play which part (accent, grounds, ink, faces, logo) and sets the measure,
navigation and on-this-page for every page. Agents build all of it over
[MCP](/developers/mcp#brand-pages).

## Publishing

Every edit to the rules, the pages or the theme is a draft. Publishing makes
the brand as it stands the version [portals](/guides/portals) show, until the
next publish:

```bash
pnpm artbucket publish --note "A warmer primary, and a page on motion"
curl -X POST https://assets.example.com/api/v1/brands/default/publish \
  -H 'Content-Type: application/json' -d '{"note": "A warmer primary"}'
```

The note (and an optional `image` beside it) is what readers see in What's
new, with what the publish changed since the one before: rules and pages
added, changed and removed. The answer names the portals showing the brand.
Publishing with nothing changed does nothing. It takes write on the
workspace, with sharing not turned off.

## Design tokens

`GET /api/v1/brand/tokens?format=css` is the brand as CSS custom properties
with `@font-face`; `format=json` is W3C design tokens.

## Brands and history

A workspace can hold several brands, one of them the default. Every change is
kept, like a shared doc: edits close together are one version, a named version
is a checkpoint, and any version can be restored, as a new version. Published
versions are marked; a restore is a draft like any edit, until it is
published.

```bash
curl https://assets.example.com/api/v1/brands/default/versions
curl -X POST https://assets.example.com/api/v1/brands/default/versions/3/restore
```
